# Ordinary artwork across compatible UI builds

Luma can now package a separate ordinary reader association for an unchanged,
previously prepared artwork producer. This avoids requiring another privileged
preparation merely because a UI-only change produces a new executable. The
original producer identity remains intact; its records are never relabelled as
if the new executable had prepared them.

The current executable, complete source-key grammar, application-ID grammar,
record parser, file reader, decoder policy, Cargo semantics and native build
selection must match the packaged association. Dependency locks and the exact
attributed PlxNative framework integration remain bound too. A present invalid
selector disables ordinary cache adoption. Only an absent selector may use the
existing current-producer path. Neither path grants publication or Root authority.

Profile and cache reads, hashing and decoding stay on the image worker. Existing
source withdrawal, generation and selection checks still govern late results.
The terminal association observation records what the worker loaded; it does
not establish current image coverage, freshness or successful drawing.

The loading treatment also changes to quiet secondary text without a graphite
plate. Available app icons retain their own shape and transparency; missing-art
fallbacks and controls can retain graphite surfaces on the OLED-black canvas.
